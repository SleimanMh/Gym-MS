# ADR 0003 — Authentication: Keycloak for login, our database for roles

- Status: accepted (Keycloak login in the admin app still to wire)
- Date: 2026-11-14

## Context
Each gym needs a branded login, optional staff SSO (Google Workspace / Microsoft Entra) and MFA, without
per-user auth fees as tenants grow (PLAN.md section 5).

## Decision
- Keycloak 26, one realm (`gym`), **one Organization per tenant with alias = tenant slug**.
  The `organization` token mapper tells the API which gym the token is for; users in several gyms request
  `organization:<alias>` after picking one.
- Keycloak authenticates. **Roles and permissions live in our database** (`tenant_memberships`, `user_roles`,
  permission bundles in `packages/shared`), so location-scoped and custom roles stay in our control and the
  API doesn't trust role claims from the IdP.
- On first Keycloak login the API links `sub` to the existing user by verified email.
- API verifies tokens via JWKS (issuer + audience `gym-api`). Access tokens 15 min, rotating refresh tokens.
- Development: `POST /v1/dev/token` mints HS256 tokens for seeded users when `AUTH_DEV_TOKENS=true`.
  Config validation refuses this flag in production.

## Consequences
- The platform console must create the Keycloak Organization when it creates a tenant (Admin API) — to do.
- Moving to a managed provider later only changes token verification and the org → tenant mapping.
